# Experiments and reports

The main API provides scenario experiment creation (`POST /experiments/scenarios`), paginated history (`GET /experiments?limit=50&offset=0`, maximum limit 100), retrieval (`GET /experiments/{id}`), and JSON or Markdown report export (`GET /experiments/{id}/report?format=json|markdown`). OpenAPI is available at `/docs`. The dashboard's Experiment History page retrieves persisted runs and can download a JSON copy.

V6 adds `POST /experiments/what-if`, which saves a typed baseline plus one to five alternatives as the existing experiment record type. Predictions are generated once per selected synthetic zone and held fixed while the capacity and connection-budget assumptions are evaluated. It adds no database table or migration; the what-if definition and result are stored additively in the existing configuration/result JSON, and the same list, retrieve, and report routes apply. Report schema 1.2 includes the scenario metrics and registry version. See [scenario workbench](scenario-workbench.md) for input bounds, formulas, allocation behavior, and API example.

V6.1 adds `POST /experiments/optimize` as an additive extension to the same record format. The request, baseline, objective, constraints, algorithm ID/version, bounded search summary, selected candidate or infeasibility result, and provenance are stored in configuration/result JSON. No migration or second database is used. Repeat retrieval only reads the saved result and never reruns prediction or optimization. Report schema 1.3 includes `optimization_analysis`; older records remain compatible with a null optimization field. Incomplete model/dataset provenance remains marked incomplete by the existing integrity checker. See [optimization](optimization.md) for formulas, stopping conditions, and interpretation.

V6.2.0 development adds `POST /experiments/robustness` for bounded one-factor synthetic demand stresses and a separate budget sweep over a saved optimization. It persists additive JSON in the same store without migration or a new database. Retrieval does not recompute it. Report schema 1.4 exposes the optional analysis while keeping older records readable. Partial evaluation and parent provenance status remain explicit. The selected test set is descriptive, not a probability or reliability estimate. See [sensitivity and robustness](robustness.md). V6.2.0 is not yet published.

Each successful record has a stable UUID, UTC creation and update timestamps, `COMPLETED` status, experiment type, schema version, validated request configuration, computed capacity results, dataset content fingerprint and algorithm, and per-zone model artifact traceability. Records are immutable after creation, so update time initially equals creation time. Failed validation or model execution returns a safe API error and does not create a partial experiment. SQLite transactions prevent partial inserts, parameterized queries are used, prior records are not overwritten, and persisted JSON is validated during retrieval. Schema `1.0`/`1.1` migrates transactionally to `1.2`, preserving records, filling update timestamps, and marking existing successful runs completed; unknown future schemas fail explicitly. The API derives an `integrity` object (`verified`, `incomplete`, or `invalid`) and stable reason codes without changing stored rows. Missing historical provenance is incomplete and not assessable; structurally invalid values are not eligible for comparison or report export. Paginated listing omits rows that cannot be decoded and returns `integrity_warnings`, preserving readable rows in the same page.

`POST /experiments/compare` accepts 2–10 unique experiment IDs. Comparisons require equal time window, dataset version and content fingerprint, classifier/regressor artifact hashes and versions, and application version; incompatible records return HTTP 409 with additive `reason_code` and optional `reason_codes`, preserving the existing `detail` string and status. Differences are calculated only for shared synthetic zone IDs and use the first ID as the baseline. Each comparison includes additive `comparison_status`, `scientific_comparability`, `comparability_reasons`, `comparability_reason_codes`, and `interpretation_detail` fields. When no zone IDs overlap, the API preserves the existing `200` response and `changes` object but marks the result `no_shared_zones` / `not_assessable` with `NO_SHARED_ZONES`; an empty change map must not be interpreted as evidence that scenarios are equivalent. Comparisons with shared zones are technically compatible but scientifically limited to the shared synthetic areas and matching recorded assumptions.

Compose initializes the database in its own `runtime-experiments` volume and mounts it writable to the main API. It persists across `docker compose down` and is removed by `docker compose down -v`; do not use the latter if you need to retain demo experiments. A local run defaults to `reports/experiments.sqlite3` and can override this with `EXPERIMENT_DB_PATH`.

JSON and Markdown exports use report schema 1.2, adding optional what-if analysis and the versioned metric registry to the integrity and assessment status, generation time, request configuration, dataset/model provenance, units, assumptions, warnings, and synthetic-data disclaimer. Existing capacity records remain readable and set the new scenario fields to `null`. Missing historical metadata is labeled “Not recorded.” Invalid nested metrics return a safe HTTP 503 rather than causing an internal error. Markdown export presents per-zone connection counts, utilization and overload and escapes user-controlled strings. Generation timestamps vary, so complete exports are not byte-identical even when deterministic input metrics match. Reproducibility is bounded by the dataset and exact model artifacts recorded with the run; it does not guarantee a future environment will load those artifacts or reproduce real-world behavior. Experiment History retrieves 25 records per page using the existing `limit`/`offset` API and reports when a selected page has no entries; integrity warnings and statuses are shown in English and Spanish.

Experiments are synthetic capacity-planning simulations, not operational network recommendations or evaluations against actual municipal telemetry.
