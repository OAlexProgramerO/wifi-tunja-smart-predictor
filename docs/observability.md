# Observability (V3.7)

V3.7 adds lightweight request correlation and structured application diagnostics to the main API and assistant API. The implementation uses the Python logging and contextvars standard-library facilities; it adds no external logging or monitoring service.

## JSON log format

Each application log record is emitted as one JSON object to the configured logging destination (normally the process console). Common fields are `timestamp` (UTC ISO 8601), `level`, `logger`, and `event`. Event records add only relevant fields, such as `service`, `request_id`, `method`, route template, `status_code`, `duration_ms`, `outcome`, operation/intent, model version, and safe error category. Duration uses a monotonic performance timer.

The event taxonomy is deliberately small:

- `http.request.completed`: one completion record per HTTP request from shared middleware. It records the safe route template (or `unmatched`), response status, duration, and outcome.
- `prediction.standard.completed` / `.failed` and `prediction.scenario.completed` / `.failed`: API prediction operations. These include model version and selected model identifier when available, never input features or coordinates.
- `assistant.chat.completed`, `assistant.scenario.completed`, `assistant.historical_query.completed`, `assistant.dataset_query.completed`, plus `.failed` or `.rejected` outcomes: deterministic assistant operations. They contain the parsed intent category and allowlisted query metric/grouping metadata where relevant.

The API route or assistant service owns the operation event; middleware owns the HTTP completion event. Uvicorn access lines are disabled because they include client IPs; the correlated lifecycle record replaces that access log. A request can therefore be searched by its request ID to connect the request lifecycle with the operation result, without duplicate lifecycle events.

## Request ID behavior

Send an optional `X-Request-ID` header. IDs containing 1–64 ASCII letters/digits plus `.`, `_`, or `-` are preserved. Missing, oversized, non-ASCII, or malformed IDs are replaced with a UUID generated by the application. The effective ID is returned in the response's `X-Request-ID` header and exposed to browser clients through CORS. IDs are bounded correlation labels and are not authentication credentials.

The middleware establishes a `contextvars` value for service logs during the request and resets it at completion, including error paths. Direct service calls outside HTTP have no fabricated request ID.

## Privacy and error handling

Logs do not include complete user messages, transcripts, raw request bodies, cookies, authorization headers, session IDs, row-level query output, feature dictionaries, or scenario coordinates. Query events include only allowlisted metric/column/grouping names. Error events use stable categories, exception class names, and at most six source-basename/function/line summaries; exception messages, local variables, and full tracebacks are not serialized. Client error payloads remain governed by the existing sanitized API handlers.

To investigate a request, copy the response `X-Request-ID` value and search the JSON log stream for the same `request_id`. Compare the request event's route, `status_code`, `outcome`, and `duration_ms` with any prediction or assistant operation event carrying that ID. Validation failures rejected before an operation handler still have a lifecycle record.

## Limits

Logs use the configured local runtime destination. This release does not add rotation, retention, durable audit storage, a log aggregator, a metrics endpoint, distributed tracing, or monitoring alerts. Operators are responsible for their runtime's log destination and retention policy. These application logs are useful diagnostics, not a complete observability platform.
