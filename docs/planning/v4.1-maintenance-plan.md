# V4.1 — Incremental Maintenance Plan

**Status:** Proposed plan only. No V4.1 implementation or release validation is claimed by this document.

**Scope:** Operational verification, artifact traceability, quality/security evidence, and documentation consistency.

**Data limitation:** All project datasets and model evaluation results are synthetic. Passing software and deployment checks will not validate forecasts against real public WiFi demand in Tunja.

## 2. Planned tasks

All checks below are **PENDING** until executed in a suitable environment and their outputs or links are recorded. A checked-in command, test, workflow, or configuration is not evidence that it passed.

### Task 1 — Docker image build and Compose configuration/startup

**Objective:** Verify the checked-in Docker build context and Compose services on a Docker-capable host using repository dependencies and documented defaults.

**Validation commands/evidence required:**

```powershell
docker compose config --quiet
docker compose build --no-cache
docker compose up -d --build
docker compose ps
docker compose logs --no-color
```

Record the host/engine context, command exit codes, built image identifier, service states, and relevant startup errors. Do not include secrets in logs or the plan.

**Acceptance criterion:** Compose configuration parses; all declared images build from the repository; startup completes without relying on untracked local artifacts or unrecorded host state; expected services reach their configured healthy state. **Status: PENDING.**

### Task 2 — Runtime initialization, health/readiness, HTTP smoke, and volume persistence

**Objective:** Demonstrate safe first initialization, repeat startup, service health/readiness, HTTP behavior, and persistence across container recreation without deleting user data.

**Validation commands/evidence required:**

```powershell
docker compose up -d --build
docker compose ps
docker compose exec -T dashboard python scripts/smoke_test.py
docker compose down
docker compose up -d
docker compose ps
docker compose exec -T dashboard python scripts/smoke_test.py
```

Inspect named volume names and expected runtime files before and after shutdown/recreation. Capture both APIs' `/health` and `/ready` outcomes and the smoke-test result. Never use `docker compose down -v` for this check. If a clean initialization test is needed, use a separate, clearly identified Compose project/volume namespace and remove only resources created for that isolated test after confirming their names.

**Acceptance criterion:** Initialization runs only as intended; both APIs report the documented health and readiness states; smoke checks cover model info, standard and scenario predictions, assistant greeting, and dashboard/backend connectivity; generated resources survive ordinary `down` and subsequent startup; logs show no unintended regeneration or data loss. **Status: PENDING.**

### Task 3 — Model metadata and prediction-version traceability

**Objective:** Verify that prediction responses and model status describe the persisted classifier artifact and distinguish artifact version from application/package version.

**Validation commands/evidence required:**

```powershell
python -m pytest tests/test_api.py tests/test_model_artifacts.py tests/test_readiness.py -q
```

Record test output for artifact metadata missing, malformed, incomplete, inconsistent, and versioned differently from the running application. On a validated deployment, save redacted `/health`, `/model-info`, and `POST /predict` response evidence demonstrating which version belongs to the app and which belongs to the artifact.

**Acceptance criterion:** Tests prove traceability and sanitized failure behavior; deployed endpoint responses match the tested contract; no version is fabricated or substituted when required metadata is unavailable. **Status: PENDING.**

### Task 4 — Python quality, dependency/security review, and CI evidence

**Objective:** Verify portable application behavior, configured quality checks, dependency/lock review, and actual CI results.

**Validation commands/evidence required:**

```powershell
python -m pytest -q
ruff check .
black --check .
python -m compileall -q api assistant_api app src scripts tests
git diff --check
```

Run the repository's appropriate dependency audit in an environment compatible with `requirements.lock` (the current lock targets Linux x86-64); record scanner/tool version, exact target/input, and findings. Review dependency pins, lock consistency, secrets/config handling, and container permissions. Inspect a real GitHub Actions run for the release-candidate commit and record its URL/SHA and job outcomes; workflow source by itself is not a passing result.

**Acceptance criterion:** The full test and configured quality commands pass; the dependency review has actionable, triaged findings or a clean scan with its scope stated; a real CI run for the reviewed commit passes all required jobs, or any failure is resolved and rerun. **Status: PENDING.**

### Task 5 — English/Spanish documentation consistency

**Objective:** Keep README, changelog, API/deployment/release history, and plan aligned with verified behavior and version surfaces.

**Validation commands/evidence required:**

```powershell
git diff --check
```

Review links, startup/stop/smoke commands, endpoint semantics, package/image/project/tag/release distinctions, synthetic-data caveats, and English/Spanish parity against the implementation and validation records from Tasks 1–4. Include references to the actual run, commit, and outstanding limitations.

**Acceptance criterion:** English and Spanish documentation makes matching claims; every validation statement is backed by recorded evidence; all unrun checks remain marked pending/blocked; synthetic metrics are explicitly synthetic and no real-world Tunja forecast validity is implied. **Status: PENDING.**

## 3. Release gates

V4.1 is **not ready for release review** until all applicable gates below pass and the documentation reflects the exact evidence:

1. Task 1 image build and Compose startup pass on a Docker-capable environment.
2. Task 2 initialization, health/readiness, full HTTP smoke, and non-destructive persistence/recreation checks pass.
3. Task 3 artifact-version traceability and failure-path tests pass, with endpoint evidence from the validated runtime.
4. Task 4 full Python suite, Ruff, Black, compilation, dependency/security review, and an actual required GitHub Actions run pass, or any exception is explicitly documented and accepted before release consideration.
5. Task 5 English/Spanish documentation is reviewed against the evidence; no pending result is described as passing.
6. Release owner separately confirms project release version, package version, image tag, Git tag, and GitHub Release decision. No values are inferred or changed by this plan.
7. Synthetic-data limitations remain explicit; no software/deployment gate may be presented as real-world predictive validation.

If a required environment is unavailable, mark its check **BLOCKED** or **PENDING**, state the prerequisite, and keep the release recommendation blocked. Do not lower the gates to produce a ready label.
