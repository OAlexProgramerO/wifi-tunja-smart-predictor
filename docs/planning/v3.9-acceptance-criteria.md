# V3.9 — Acceptance Criteria & Verification Plan

**Planned release:** V3.9 — One-Command Docker Setup & Reliability  
**Planned package version:** `0.3.9`  
**Baseline:** V3.8 (`0.3.8`)  
**Status:** Planning only; the checklist must be completed with observed results during implementation.

## 1. Acceptance summary

V3.9 is intended to make a clean clone start using Docker Compose without host-side Python setup, manual package installation, manual synthetic dataset generation, or manual model training. A Docker-capable environment is required to prove the end-to-end claim.

Use these status values in the final engineering report:

- `PASS` — command/test was executed and passed.
- `FAIL` — executed and failed.
- `NOT RUN` — not executed.
- `BLOCKED` — could not execute due to a stated prerequisite or environment limitation.
- `NOT APPLICABLE` — supported by a brief technical explanation.

Never mark a check as PASS because the configuration looks correct or because a test was added. A CI workflow edit is not proof until the workflow actually runs.

## 3. Clean-clone and dependency criteria

- [ ] A clean checkout includes or can safely initialize all required model artifacts, metadata and dataset resources.
- [ ] The Docker image does not rely on `.venv`, globally installed host packages, ignored assets, private paths or untracked files.
- [ ] Runtime dependency installation follows the repository's authoritative configuration.
- [ ] Conflicting or duplicated dependency declarations have been eliminated only where required and justified.
- [ ] Python version in the image is compatible with the project's declared support range and compiled dependencies.
- [ ] The application starts without a host Python installation.
- [ ] The documented default workflow does not require `.env`, paid services, API keys or external model credentials.
- [ ] If resource initialization is necessary, it runs once in a controlled stage, does not race among services, does not overwrite user data unexpectedly and fails visibly when incomplete.

## 4. Dockerfile and Compose criteria

- [ ] `docker compose config` exits successfully using default configuration.
- [ ] `docker compose build` succeeds from a clean checkout on a Docker-capable environment.
- [ ] The base image uses a deliberate, compatible version rather than an unpinned `latest` tag.
- [ ] Application processes run as non-root where practical and required capabilities are not added without justification.
- [ ] `.dockerignore` excludes `.git`, virtual environments, caches and secrets without excluding runtime assets.
- [ ] Main API, assistant API and dashboard are defined with correct entry points and ports.
- [ ] Required service startup dependencies are explicit; readiness conditions are used when supported.
- [ ] Host ports bind to loopback by default unless a documented requirement calls for broader exposure.
- [ ] No secrets are baked into image layers or logged.
- [ ] Restart policies and shutdown behavior are suitable for a local demo and documented.
- [ ] Container logs remain available through Docker's normal stdout/stderr collection.
- [ ] No health check depends on an executable absent from the selected image.

## 5. Configuration and networking criteria

- [ ] Configuration defaults work for a fresh clone.
- [ ] Supported environment overrides are documented and tested.
- [ ] Invalid explicit configuration fails clearly rather than silently falling back to an unrelated host.
- [ ] Server-side inter-container calls use Compose DNS names.
- [ ] Browser-facing URLs are correct for the user's browser and are not replaced with container-only hostnames.
- [ ] Local development outside Docker continues to work with documented defaults.
- [ ] CORS remains limited to intended origins and current security behavior is preserved.
- [ ] Error messages are actionable but do not disclose secrets, filesystem paths or stack internals to API clients.

## 6. Health, readiness and recovery criteria

- [ ] Existing `/health` endpoint status and response contract remain backward-compatible for both APIs.
- [ ] Main API readiness accurately reports whether the resources needed for its supported prediction operations are available.
- [ ] Assistant API readiness accurately reports whether required resources for its supported operations are available.
- [ ] Missing resources produce an unhealthy/not-ready result and do not leak internal paths.
- [ ] Health checks are lightweight, bounded and do not regenerate datasets or retrain models.
- [ ] The dashboard waits for required APIs to be available where Compose supports this behavior.
- [ ] A service that cannot become ready is diagnosable through container status and logs.
- [ ] Repeated start/stop cycles do not trigger unnecessary model training or destructive dataset generation.

## 7. Application smoke-test criteria

A deployment smoke test must run against the real local Compose deployment and return a nonzero exit code when a required check fails.

- [ ] Main API `/health` returns the expected successful status and shape.
- [ ] Main API readiness returns the expected ready status and shape.
- [ ] Assistant API `/health` returns the expected successful status and shape.
- [ ] Assistant API readiness returns the expected ready status and shape.
- [ ] Main API model information endpoint responds with the documented schema.
- [ ] A valid prediction request returns the existing documented response schema.
- [ ] A representative scenario prediction succeeds, if included in the implemented smoke suite.
- [ ] A simple assistant greeting returns the expected response without external credentials.
- [ ] Dashboard HTTP endpoint responds successfully.
- [ ] Dashboard-to-API and dashboard-to-assistant communication is actually exercised, not merely inferred from open ports.
- [ ] The test uses real documented payloads and does not depend on real municipal data or live network infrastructure.
- [ ] Error output identifies which check failed without exposing secrets or full sensitive payloads.

## 12. Release blockers

V3.9 should not be described as fully validated if any of the following applies:

- A required dataset/model artifact is absent from a clean build and there is no verified initialization strategy.
- Any service depends on `localhost` when it must reach another container.
- The dashboard starts but cannot communicate with its APIs.
- Readiness reports success while required resources are missing.
- Core unit/regression tests fail without an understood and documented pre-existing cause.
- Security or privacy protections are weakened.
- Documentation assumes commands, URLs, or startup behavior that do not work.
- The implementation report claims unexecuted checks passed.

## 14. Scope reminder

The goal is a dependable local demonstration setup, not a guarantee that software can never fail on any machine. Docker must be installed and running, ports must be available, and the computer must have sufficient resources. The application continues to use synthetic data; a successful container deployment does not validate real-world demand forecasts or actual Tunja WiFi infrastructure.
