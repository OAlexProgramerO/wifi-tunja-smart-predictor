# WiFi Tunja Smart Predictor V4.2.0 — implementation and validation record

**Status: implementation candidate; not a stable release.** The Python package candidate is `0.4.2`; the project release label is `V4.2.0`. Docker runtime and GitHub Actions evidence are required before considering an annotated `v4.2.0` tag or GitHub Release. The existing `v4.1.0` tag is preserved.

All datasets, persisted models, and reported evaluation metrics are synthetic. Passing software tests does not validate forecasts against real public WiFi demand in Tunja.

## Implemented improvements

- Classifier and regressor loaders deserialize a single byte snapshot and return its SHA-256 digest and size. Standard and scenario predictions include a UTC timestamp, prediction UUID, request ID, app version, model version, selected model, and artifact identity without filesystem paths.
- Training metadata now carries a shared `training_run_id`. Readiness, model information, and scenario initialization compare that ID and related split/dataset/preprocessing metadata so artifacts from separate training runs are not combined. Legacy bundles without run IDs remain supported when their training timestamps and metadata agree.
- Dataset validation rejects non-numeric strings in required numeric columns, non-finite values, timezone-aware or inconsistent timestamps, and conflicting rows for the same access-point/hour. Exact duplicate rows remain governed by the existing synthetic-data tolerance.
- Classification/regression evaluation validates prediction shapes, finite values, supported labels, and probability distributions before metrics can be recorded.
- The scenario dashboard labels binary demand classification separately from next-hour connection regression, explains interval limits, presents artifact provenance, and shows generic user-facing errors while logging diagnostics.
- CI supports manual dispatch, read-only repository permissions, Python compilation, and a scoped audit of hash-locked runtime dependencies.
