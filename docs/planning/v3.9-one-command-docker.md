# V3.9 — One-Command Docker Setup & Reliability

**Project:** WiFi Tunja Smart Predictor  
**Planned package version:** `0.3.9`  
**Current baseline:** V3.8 — Reproducible Deployment & Operational Readiness (`0.3.8`)  
**Status:** Planning only. No implementation, commit, tag, or release is implied by this document.

## 1. Objective

Make a fresh clone runnable with Docker Compose using one primary command:

```powershell
docker compose up --build
```

The standard demonstration workflow must not require the user to install Python packages on the host, create a virtual environment, generate the synthetic dataset manually, or train models manually. Docker Desktop (or Docker Engine with Compose) remains a prerequisite; the project cannot install or configure the host's Docker engine itself.

V3.9 should improve the reliability of V3.8's container setup rather than redesign the ML system. The three expected services are the main FastAPI API (normally port 8000), the assistant API (normally port 8001), and the Streamlit dashboard (normally port 8501). Confirm real entry points, names, ports, and URLs from the repository before changing configuration.

## 5. Architecture and startup design

### 5.1 Three application services

Use the existing app entry points, subject to verification:

- Main API: typically `api.main:app`, exposed locally on port 8000.
- Assistant API: typically `assistant_api.main:app`, exposed locally on port 8001.
- Dashboard: typically `app/dashboard.py`, exposed locally on port 8501.

Reuse a common app image where the dependency/runtime requirements permit it. Avoid separate duplicate images unless there is a concrete reason.

### 5.2 Service URLs

Inside Compose, `localhost` refers to the current container. Use Compose service DNS names for server-side inter-service calls, for example `http://api:8000` and `http://assistant-api:8001`, if those are the actual service names. Preserve host-facing `http://localhost:...` behavior where the browser itself makes calls. Identify whether each request originates in a browser or inside a container before selecting a URL.

### 5.3 Resource initialization decision

First inventory required assets and verify Git tracking/build-context inclusion. If all required data and models can be packaged appropriately, prefer that simpler route. If some must be generated, reuse the existing supported scripts and add one explicit initialization stage only when necessary. The main API, assistant API and dashboard must not independently race to create the same files. A failed initializer must block dependent services from becoming ready and show a safe, actionable error.

### 5.4 Health and readiness

Keep `/health` behavior backward-compatible. Readiness should verify only resources genuinely required to serve the service's supported operations. Checks must be cheap, bounded, non-sensitive and free from retraining or dataset regeneration. Compose health checks must not invoke `curl` unless the image actually installs it; use an available HTTP client or another verified approach.

### 5.5 Local exposure and secrets

Bind host ports to loopback by default unless an explicit project requirement says otherwise. Do not require a secret for local demonstration. Keep application logs on stdout/stderr and preserve request IDs, structured event logging, log privacy, body limits, CORS rules, security headers and input validation.

## 7. Expected first-run instructions

The finished deployment should support:

```powershell
git clone https://github.com/OAlexProgramerO/wifi-tunja-smart-predictor.git
cd wifi-tunja-smart-predictor
docker compose up --build
```

Expected local URLs, subject to verification against Compose:

- Dashboard: `http://localhost:8501`
- Main API docs: `http://localhost:8000/docs`
- Assistant API docs: `http://localhost:8001/docs`

Useful operations:

```powershell
docker compose ps
docker compose logs -f
docker compose down
```

The standard path must not require an `.env` file if safe defaults are sufficient. Document how to override settings when needed and whether data/volumes persist after shutdown.
